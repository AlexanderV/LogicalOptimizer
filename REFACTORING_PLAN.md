# Результуючий план рефакторингу LogicalOptimizer

Зведення трьох джерел:

1. **Емпіричний аудит якості мінімізації** — вичерпне порівняння з еталонним Quine–McCluskey
   (усі 254 функції n=3 та всі 65 534 функції n=4; гарнес: scratchpad `MinEval/`).
2. **Ревью класичних кейсів мінімізації** (~45 CLI-кейсів) і **структурне ревью пайплайна оптимізаторів**.
3. **CODE_REVIEW_REFACTORING_PLAN.md** — архітектурне ревью (AST, конвеєр, API); релевантні пункти
   інтегровані нижче з посиланнями виду *(арх. §N)*.

## Ключові факти, що визначають пріоритети

| Факт | Значення |
|---|---|
| Нееквівалентний результат оптимізації | **15.0%** функцій n=3, **36.9%** n=4 |
| Причина | несумлінне одночасне видалення взаємно-обґрунтованих консенсусних термів у `RedundancyOptimizer.SimplifyConsensusRedundancy` |
| Серед коректних: гірше за мінімум | 12% (n=3), 36.4% (n=4; в середньому +10 літералів, до +46) |
| Серед коректних: краще за мінімальний SOP (факторизація) | 42–47% — сильна сторона, зберегти |
| Швидкість | 0.5–5 мс/вираз — величезний запас на точні алгоритми |

Висновок: теза архітектурного ревью «основний потенціал не в нових правилах» спростована даними.
Пріоритет: **коректність → якість результату → архітектура, що їх підтримує → API/інфраструктура**.

## Фаза 0 — Коректність (блокер; до будь-яких інших змін) — ✅ ВИКОНАНО

**0.1. Виправити `SimplifyConsensusRedundancy`** (`Optimizers/RedundancyOptimizer.cs:103-164`).
Видаляти консенсусні терми ітеративно по одному, після кожного видалення переперевіряючи проти
*поточного* списку: терм можна прибрати лише поки обидва його «батьки» присутні.
Найменше відтворення: `!a&!b&!c | !a&b&!c | a&b&!c | !a&!b&c | a&!b&c` → зараз `b&!c | c&!b` (втрачено мінтерм 000).

**0.2. Запобіжник еквівалентності в пайплайні.** У `BooleanExpressionOptimizer` для виразів
до ~14 змінних звіряти таблицю істинності результату з вихідною; при розбіжності повертати вхідний
вираз (і фіксувати інцидент у метриках). Страхує від будь-якого майбутнього несумлінного правила.

**0.3. Регресійна база.**
- Тести на всі 38 функцій n=3, що ламаються зараз.
- Nightly/`Category=Exhaustive`: повний перебір n≤4 проти QM (перенести гарнес `MinEval/Program.cs`).
- Property-based тести: випадковий AST → optimize → перевірка еквівалентності *(арх. «Зафіксувати поведінку»)*.

**0.4. Валідація вхідних меж** *(арх. P0-1, P0-2)*:
- CSV: імена змінних за граматикою лексера, заборона `0`/`1`/дублікатів/кількох result-колонок,
  явний ліміт кількості змінних, безпечне визначення повноти таблиці (без `1 << n` на n>30).
- `TruthTable`: інваріанти конструктора (`results.Count == 2^n`, унікальність змінних),
  `IReadOnlyList` + defensive copy замість публічних mutable `List`.

## Фаза 1 — Якість результату (найбільший виграш на одиницю зусиль) — ✅ ВИКОНАНО

**1.1. Точний бекенд `TruthTableMinimizer`** — Quine–McCluskey + метод Петріка (або branch-and-bound
покриття) за поріг ~≤12–14 змінних. Інфраструктура таблиць уже є; еталонна реалізація з
`MinEval/Program.cs` — готова основа. Закриває: колапс на щільних функціях (+46 → 0), пропущені
широкі прайми, CNF-консенсус, «розшир-скороти» долини.

**1.2. Фінальний вибір відповіді.** `Optimized` = найдешевший за **літералами** з
{результат пайплайна, факторизований мін-SOP, мін-POS}. Пайплайн залишається для n понад поріг
і як джерело факторизованих форм (його доведена перевага).

**1.3. Don't-care з CSV.** Часткова таблиця має віддавати (мінтерми + DC-множина), а не примусову
DNF; QM використовує DC для дешевшого покриття (зараз XOR-подібна часткова таблиця дає 4 літерали
замість досяжних 2). Виконувати разом із 0.4-CSV.

**1.4. Мінімізовані нормальні форми.** Для малих n — CNF/DNF з QM (мін-POS/мін-SOP); для великих —
пост-обробка `NormalFormConverter`: видалення суперечливих термів, дублікатів літералів, поглинутих
клауз (зараз `--dnf` може містити `a & !a`, `--cnf` — надлишкові резольвенти).

## Фаза 2 — Архітектура переписувача (робить правила простими і повними)

**2.1. `ConstantNode` + повністю immutable AST** *(арх. §3, P2-10)* — ✅ ВИКОНАНО (Clone збережено як частину API вузлів).
Прибирає клас помилок «`VariableNode("0")` — не змінна» і дозволяє безпечне шеринг-переиспользування піддерев.

**2.2. N-ary `AndNode`/`OrNode` + єдиний канонізатор** *(арх. §3-4, P1-7)*: сплющення, нейтральні/поглинаючі
константи, `Distinct`, пошук `x`/`!x` через `HashSet`, стабільне сортування. Ліквідує
`AssociativityOptimizer`, більшість `CommutativityOptimizer`/`ConstantsOptimizer`, частину
`ComplementOptimizer`, і всі розсипані `FlattenAnd/FlattenOr/Aggregate`.

**2.3. Rewrite-конвеєр `IRewriteRule`** *(арх. §5, P1-6)* — ⚙ ЧАСТКОВО (per-node прийняття консенсусу + детекція циклів зроблені; єдиний конвеєр — разом з 2.1-2.2): один bottom-up прохід, чисті локальні
правила без власних обходів; єдина cost-функція (літерали → оператори → глибина); прийняття
переписування **на рівні вузла** (замість whole-tree rollback, який зараз блокує покращення в
одному піддереві через зростання в іншому); детекція циклів через структурний хеш і чесний статус
`Converged / CycleDetected / IterationLimit` *(арх. P1-8)*.

**2.4. Повнота правил** (для n понад QM-поріг) — ✅ ВИКОНАНО (без зворотного Де Моргана — конфліктує з задокументованим форматом виводу):
- дзеркальна полярність розширеного поглинання: `!X | X&Y → !X | Y`;
- поглинання зі складеним абсорбером (через NNF-заперечення): `a&b | !(a&b)&c → a&b | c`;
- дуальний консенсус на клаузах (CNF-сторона): `(a|b)&(!a|c)&(b|c) → (a|b)&(!a|c)`;
- контрольований expand-reduce: локальна дистрибуція → спрощення → прийняти лише при зниженні cost
  (використати наявний `DistributiveOptimizer`);
- факторизація по підгрупах термів і all-pairs по сплющеному списку (без залежності від сусідства);
- set-операції замість O(n²) циклів: subset-check для поглинання, перетин множин для факторів *(арх. §6)*;
- завершальний зворотний Де Морган (`!a&!b&!c → !(a|b|c)` де дешевше за cost-функцією).

**2.5. Форматування окремо від семантики** *(арх. P1-5)* — ✖ ВІДХИЛЕНО СВІДОМО: дужки факторизованих груп — задокументована фіча формату виводу; прапорець вже виключений з рівності. Прибрати `ForceParentheses`,
дужки визначає formatter за пріоритетами. Робити останнім кроком фази — зачіпає багато тестів на точні рядки.

## Фаза 3 — API та інфраструктура *(арх. §2, §7, §8)* — ✅ ВИКОНАНО (3.1 OptimizationOptions, 3.2 ComputationStatus+DebugInfo, 3.4 internal+IVT, 3.5 editorconfig+format-check+доки; SAT/BDD з 3.3 — майбутнє)

**3.1.** `OptimizationRequest` з прапорцями `Optimize|CNF|DNF|Advanced|TruthTable|Metrics` —
не рахувати обидві нормальні форми, коли потрібна одна або жодна.
**3.2.** Типізований `ComputationResult<T>` (`Computed/TooLarge/NotRequested`) замість сентинела `"-"`;
прибрати `Console.WriteLine` з бібліотечного фасаду (debug — як дані/logger).
**3.3.** Експоненційні операції (CNF/DNF/таблиці) — окремі сервіси з budget; для еквівалентності
понад поріг — SAT/BDD (майбутнє; або Espresso-цикл, якщо великі n стануть реальним сценарієм).
**3.4.** Звуження API: implementation-типи → `internal` + `InternalsVisibleTo` для тестів.
**3.5.** Синхронізація документації (`copilot-instructions.md`: .NET 8 → 10, видалений `--test`;
README: placeholder-URL) і `.editorconfig` + `dotnet format --verify-no-changes` у CI.

## Порядок виконання і очікуваний ефект

| Крок | Обсяг | Ефект |
|---|---|---|
| Фаза 0 | малий | зникають 15–37% хибних результатів; межі входу захищені |
| Фаза 1 | середній | гарантований мінімум (або краще, з факторизацією) для всіх виразів ≤12–14 змінних; чисті CNF/DNF; don't-care |
| Фаза 2 | великий (один узгоджений цикл, не локальні правки) | −30–40% коду оптимізаторів; повнота правил для великих n; чесна збіжність |
| Фаза 3 | середній | швидший API без зайвих обчислень; вужча публічна поверхня; CI-контроль формату |

Фази 0–1 незалежні від архітектурної перебудови і дають основний практичний виграш одразу.
Фазу 2 виконувати єдиним циклом (n-ary AST → канонізатор → конвеєр → правила), інакше подвійна робота.
Пункти архітектурного ревью, що вже виконані раніше (instance-стан `NormalFormConverter`, видалення
мертвого `ValidateIterations`-виклику, оновлення пакетів, CI build+test), до плану не включені.
