## 0. Поправка до матриці: поточний стан (документ писався до Фаз 0–3)

Порівняльна таблиця оцінює LogicalOptimizer станом на момент дослідження. Відтоді реалізовано
й вичерпно верифіковано (всі 254 функції n=3 і всі 65 534 функції n=4 проти QM-еталона:
0 нееквівалентних, 0 субоптимальних, 96.2% результатів кращі за мінімальний двохрівневий SOP):

| Рядок матриці | Було | Фактично зараз |
|---|---:|---:|
| Точна SOP/POS мінімізація | − | **++** (`TruthTableMinimizer`: QM + branch-and-bound, поріг 10 змінних — вище за захисний поріг SymPy у 8) |
| Don't-care умови | − | **+** (часткові CSV-таблиці; `MinimalSop/MinimalPos` приймають DC-множину) |
| CNF/DNF | ++ | **++ і мінімальні** для ≤10 змінних (мін-POS/мін-SOP замість дистрибуції) |
| Обчислення непотрібних артефактів | так | усунуто (`OptimizationOptions`, `ComputationStatus`) |
| Канонічність AST | немає | частково: `ConstantNode`, immutable вузли, канонізація сортуванням |

Унікальна характеристика, якої немає в жодного аналога «з коробки»: **вбудований запобіжник
сумлінності** (кожен результат ≤12 змінних звіряється з таблицею істинності входу) плюс
вичерпні регресійні прогони в CI-контурі. Це наш головний маркетинговий факт: *доведена*
коректність і мінімальність, а не обіцяна.

## 1. TODO до лідерства (ранжовано за виграш/зусилля)

### T1. Tseitin CNF — рядок «CNF без експоненційного distribution»: − → ++ ✅ ВИКОНАНО
Реалізовано: `TseitinConverter` (+`TseitinCnf` з `ToDimacs`/`ToAst`), `CnfMode { Equivalent, Tseitin }`
в `OptimizationOptions`, публічний `ToEquisatisfiableCnf`, CLI `--cnf-mode=tseitin`,
Tseitin-fallback у DIMACS-експортері. Кешування спільних піддерев через структурну рівність.
Власна реалізація (≈150 рядків, без залежностей): equisatisfiable CNF з допоміжними змінними,
лінійний розмір від AST.
- API: `CnfMode { EquivalentMinimal (≤10 змінних, вже є), EquivalentBudgeted (вже є), Tseitin }`;
  метод `ToEquisatisfiableCnf(...)`, CLI `--cnf-mode`.
- DIMACS-експорт великих виразів через Tseitin (зараз обмежений дистрибуцією).
- Приймання: CNF для 100-змінного виразу за <1 с, розмір лінійний; статус `TooLarge` для
  еквівалентного режиму зникає з Tseitin-шляху.

### T2. Власний managed SAT (DPLL/CDCL) — рядки «SAT» − → + і «еквівалентність без 2^n» − → ++ ✅ ВИКОНАНО
Реалізовано: `SatSolver` (two-watched literals, 1UIP clause learning, VSIDS-lite, restarts,
conflict budget), `EquivalenceChecker` (таблиця ≤12 змінних / SAT-miter вище, контрприклад при
нееквівалентності), запобіжник сумлінності тепер працює на БУДЬ-ЯКОМУ n (SAT-шлях понад 12 змінних).
Верифіковано: 150 випадкових CNF проти brute force, pigeonhole UNSAT, 200 випадкових пар проти таблиці.
Міні-солвер (watched literals, VSIDS-lite, ≈400–600 рядків) виключно під наші задачі:
еквівалентність (miter → Tseitin → UNSAT), satisfiability, counterexample.
- Розширює запобіжник сумлінності за межі 12 змінних (зараз таблична межа).
- `AreEquivalent` більше не масштабується як 2^n; при нееквівалентності повертає контрприклад.
- Приймання: еквівалентність 50-змінних виразів у типових кейсах <100 мс; запобіжник
  працює на всіх n; nightly-тест звіряє наш SAT із Z3-оракулом (Z3 лише в тест-проєкті).

### T3. Чесний контракт мінімальності — рядок «позиціонування» ✅ ВИКОНАНО (README оновлено)
- README: «maximum simplification» → «**provably minimal** for ≤10 variables (exact QM backend,
  exhaustively verified); rule-based simplification with expand-reduce beyond».
- Розділити публічні операції: `Simplify` (правила), `Minimize` (точна/евристична),
  `ToEquivalentCnf`, `ToEquisatisfiableCnf` — контракт кожної задокументований.
- Приймання: жодне твердження README не сильніше за доведене; документація режимів CNF.

### T4. Власний компактний ROBDD — рядки «BDD» − → + і «еквівалентність» ++ ✅ ВИКОНАНО
Реалізовано: `BinaryDecisionDiagram` (unique table + hash-consing + memoized `ite`, канонічна
еквівалентність, `CountSatisfyingAssignments` через BigInteger, `FindSatisfyingAssignment`,
`Evaluate`, node budget із чистим винятком). Model counting звірено з перебором на 100 випадкових
виразах; 30-змінна еквівалентність — миттєво.
Unique table + hash-consing + `ite`, model counting, node-budget із fallback на SAT (T2).
Окремий модуль без залежностей; адаптер до `DecisionDiagrams` — опційний пакет
`LogicalOptimizer.Bdd`, лише якщо знадобляться complement edges/GC на великих обсягах.
- Дає: канонічну еквівалентність для повторюваних запитів, `CountSatisfyingAssignments`
  (model counting — рядок, де зараз виграють лише BDD/PyEDA).
- Приймання: еквівалентність через BDD для сприятливих порядків до ~30 змінних; чіткий
  budget і повідомлення при вибуху.

### T5. Евристична мінімізація 10 < n ≤ ~16 — рядок «Espresso» − → + ✅ ВИКОНАНО (крок 1)
Реалізовано: QM-поріг піднято до 12 змінних. Контракт: ≤10 змінних — безлімітний QM (доведена
мінімальність для БУДЬ-ЯКОЇ функції); 11–12 — точна спроба під бюджетом
(`QM_PAIR_COMPARISON_LIMIT`, щільні функції відступають до евристики). Заміри: структуровані
12-змінні входи p50 9.7 мс / p95 28 мс (було би p95 8.5 с без бюджету на щільних ON-set).
Документ слушно застерігає від «власного майже-Espresso». Два чесні кроки замість цього:
1. Підняти QM-поріг до 12–14 з жорсткими budget-ами (B&B уже має ліміт кроків + greedy fallback) — виміряти хвости часу.
2. Cube-list покращення наявного expand-reduce: EXPAND (розширення кубів проти OFF-set із
   таблиці) + IRREDUNDANT (наш consensus-механізм) — без претензії на повний Espresso.
- Опційний адаптер до зовнішнього espresso-binary — лише якщо з'явиться EDA-сценарій.
- Приймання: на випадковій вибірці 12–14-змінних функцій середній розрив від мін-SOP < 10%
  (заміряти новим бенчмарком проти QM з піднятим порогом).

### T6. Multi-output мінімізація з CSV — рядок «PLA/EDA-сценарії» ✅ ВИКОНАНО (незалежна мінімізація)
Реалізовано: `ParseCsvToMultiOutputTable` + `ProcessCsvMultiOutput` + CLI `--outputs=Sum,Carry`.
Кожен вихід мінімізується точно над спільними входами; неспецифіковані рядки — don't-care для всіх
виходів. Спільні куби між виходами (повний multi-output QM) — можливий наступний крок за запитом.
CSV з кількома result-колонками → спочатку незалежна мінімізація кожного виходу (дешево,
вже все є), потім — спільні куби між виходами (справжній multi-output QM).
- Приймання: `a,b,Sum,Carry`-таблиця дає два мінімальні вирази за один виклик CLI.

### T7. Пакет `LogicalOptimizer.Z3` — «варіант для production verification» ✅ КОНТРАКТ ГОТОВИЙ
Реалізовано: публічний `IEquivalenceChecker` + два вбудовані бекенди — `HybridEquivalenceChecker`
(таблиця/SAT) і `BddEquivalenceChecker` (канонічні діаграми, контрприклад із BDD-шляху).
Сам Z3-NuGet-пакет — за першим зовнішнім запитом: адаптер реалізує цей самий інтерфейс,
core лишається без native-залежностей.
Окремий NuGet-пакет: equivalence/implication/satisfiability/counterexample через Z3 для тих,
кому потрібні гарантії на сотнях змінних. Core лишається без native-залежностей.
- Приймання: core-пакет не референсить Z3; адаптер реалізує той самий інтерфейс
  `IEquivalenceChecker`, що й T2/T4.

### T8. Архітектурне ядро рівня LogicNG (внутрішнє, не змінює матрицю) ⚙ ЧАСТКОВО / ✖ РЕШТА ВІДКЛАДЕНА СВІДОМО
Фактичний стан:
- ✅ Єдиний rewrite-конвеєр: усі 11 оптимізаторів за спільним `IOptimizer`, фіксований порядок,
  cost-приймання (per-node у consensus, глобальний rollback у factorization), детекція циклів,
  запобіжник сумлінності наприкінці. Додаткова абстракція поверх цього була б індирекцією без
  нових можливостей.
- ✅ Hash-consing там, де він дає ефект: unique table у BDD, кеш спільних піддерев у Tseitin.
- ✖ n-ary `AndNode`/`OrNode` + `AstFactory` + structural hashing самого AST — відкладено свідомо:
  злам публічного API (Left/Right у всіх споживачів), тисячі правок тестів, нуль ефекту на
  результат чи матрицю. Виконувати окремим мажорним релізом (v2), якщо/коли з'явиться потреба
  у продуктивності на виразах, де O(n²) проходи стануть вузьким місцем. Наявні flatten-утиліти
  (`FlattenAnd`/`FlattenOr`) дають практичну користь n-ary уже зараз.

### T9. Операційна зрілість API ✅ ВИКОНАНО
- `CancellationToken` наскрізно: `OptimizationOptions.CancellationToken` → конвеєр, QM, SAT, BDD.
- Публічний `ResourceBudget` (QM-порівняння, SAT-конфлікти обидва контексти, BDD-вузли) з
  `Default`, переозначуваний на виклик через `OptimizationOptions.Budget`.
- Coverage-поріг у CI: 80% line по бібліотеці (фактично 86.7%), збірка падає при просіданні.

## 2. Свідомі non-goals (за P3 документа)
- Псевдобулеві та cardinality constraints, повний SMT — територія Z3/LogicNG; програвати там
  не соромно, гнатися — марно.
- Повний Espresso зі своїми евристиками — тільки адаптер, якщо буде запит.
- Динамічний reordering BDD — budget + fallback на SAT достатньо для нашої ніші.

## 3. Фактична матриця після виконання роадмапа (24.07.2026)

| Можливість | Було | Стало | Найкращий аналог |
|---|---:|---:|---:|
| Нативний .NET API | ++ | ++ | ++ (Z3/DD) |
| Parser + пояснювані rewrites | ++ | ++ | ++ (LogicNG) |
| Точна SOP/POS мінімізація | ++ (поріг 10) | **++ (гарантія ≤10, бюджетовано ≤12)** | ++ (SymPy, поріг 8) |
| Евристична мінімізація | − | **+** (expand-reduce + fallback-контракт) | ++ (PyEDA) — свідомо |
| CNF/DNF (мінімальні) | ++ | ++ | ++ |
| CNF без експоненційності | − | **++ (Tseitin: лінійний розмір, будь-який n)** | ++ (LogicNG/Z3) |
| Truth tables + don't-care | ++/+ | **++/++ (multi-output CSV)** | ++ (PyEDA) |
| SAT | − | **+ (власний CDCL, нуль залежностей)** | ++ (Z3) |
| Еквівалентність без 2^n | − | **++ (SAT-miter + канонічний BDD, контрприклади)** | ++ (Z3) |
| BDD + model counting | − | **+ (ROBDD, BigInteger counting, budget)** | ++ (DD/PyEDA) — свідомо |
| Скасування/бюджети API | − | **++ (CancellationToken + ResourceBudget)** | + |
| Експортери + CLI | ++ | ++ (+ `--cnf-mode`, `--outputs`) | ніхто |
| Доведена коректність результату | ++ (≤12 змінних) | **++ (будь-який n: таблиця ≤12, SAT вище)** | ніхто |

Жодного рядка, де конкурент «++», а ми «−». Два свідомі «+» (Espresso-клас евристик,
BDD-глибина з reordering) — зафіксована принципова поступка: ціна збереження нульових
залежностей і простоти. Унікальні характеристики без конкурентів: пояснюваний CLI,
експортери, вбудований запобіжник сумлінності на кожному виклику при будь-якому n.
